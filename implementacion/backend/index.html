Backend

API REST de VigiaSenior

Esta carpeta recoge la parte técnica principal del proyecto: el backend en Node.js, TypeScript, Express y Prisma. Aquí se define cómo se reciben las peticiones, cómo se procesan los eventos del sistema, cómo se consulta la base de datos y qué respuestas devuelve la API.

Qué papel tiene este backend

En VigiaSenior, el backend es la pieza que da sentido a lo que ocurre en el sistema. El dispositivo o la simulación pueden enviar eventos, pero es el backend quien debe interpretarlos, relacionarlos con la planificación diaria y actualizar el estado de cada toma.

No se trata solo de tener rutas que respondan. El objetivo es que la API sea coherente: que reciba datos válidos, aplique reglas de negocio, guarde información útil y permita consultar el estado del paciente, del dispositivo y de las alertas.

Cómo leer esta carpeta

Si es la primera vez que entras en el backend, no conviene abrir archivos al azar. Una forma sencilla de entender el proyecto es seguir el recorrido de una petición: primero la ruta, después el controlador, luego el servicio y finalmente el repositorio.

  • Ruta: define el endpoint que recibe la petición.
  • Controlador: recoge parámetros y cuerpo, valida lo necesario y prepara la respuesta HTTP.
  • Servicio: aplica la lógica de negocio del proyecto.
  • Repositorio: realiza las operaciones de lectura y escritura con Prisma.
  • Tests: comprueban que los endpoints y la lógica se comportan como se espera.

Qué hay que revisar

Estos son los puntos principales que conviene localizar antes de empezar a modificar código. La idea es saber dónde vive cada responsabilidad y evitar mezclar lógica de negocio, consultas a base de datos y respuestas HTTP en el mismo sitio.

  • src/routes: entrada de la API. Aquí se declaran los endpoints.
  • src/controllers: gestión de la petición y la respuesta HTTP.
  • src/services: reglas de negocio y decisiones importantes del sistema.
  • src/repositories: acceso a datos con Prisma.
  • src/validators: validación de parámetros y cuerpos de petición.
  • src/types: tipos compartidos entre capas.
  • tests: pruebas de endpoints y de lógica.

Flujo básico de una petición

Cuando se llama a un endpoint de VigiaSenior, el recorrido normal es parecido a este:

  1. El cliente, Postman o el simulador envía una petición a la API.
  2. La ruta identifica qué controlador debe ejecutarse.
  3. El controlador valida los datos recibidos y llama al servicio correspondiente.
  4. El servicio aplica la lógica de negocio: comprueba estados, ventanas temporales, eventos o alertas.
  5. El repositorio consulta o actualiza la base de datos usando Prisma.
  6. El backend devuelve una respuesta clara al cliente.

Entender este flujo ayuda mucho a depurar errores. Si algo falla, no siempre hay que tocarlo todo: primero conviene localizar en qué capa está el problema.

Comandos habituales

Estos comandos permiten preparar el entorno, generar Prisma, aplicar migraciones, cargar datos iniciales, ejecutar pruebas y compilar el proyecto. Antes de programar una nueva ruta, merece la pena comprobar que el backend levanta correctamente. 

cd implementacion/backend
npm install
cp .env.example .env
npx prisma generate
npx prisma migrate dev --name init
npm run prisma:seed
npm test
npm run build
npm run dev

Endpoints principales

Estos endpoints forman el núcleo funcional del backend. Sirven para comprobar que el servidor responde, consultar la planificación diaria, registrar eventos del dispositivo, revisar el estado del paciente y gestionar alertas.

Método Ruta Uso
GET /health Comprobar que el servidor responde.
GET /api/devices/:deviceId/schedule/today Consultar el plan del día del dispositivo.
POST /api/devices/:deviceId/events Registrar eventos del pastillero o de la simulación.
GET /api/patients/:patientId/dashboard Consultar un resumen del estado del paciente.
GET /api/patients/:patientId/alerts Consultar alertas asociadas al paciente.
PATCH /api/alerts/:alertId/resolve Resolver una alerta abierta.
Regla clave: una apertura de cajita no confirma la toma. Para marcar una toma como correcta debe haber apertura y confirmación dentro de la ventana definida. Esta regla afecta a la lógica del servicio, a los eventos guardados y al estado final que devuelve la API.

Antes de tocar código

Una recomendación sencilla: no empieces modificando servicios o repositorios sin haber probado antes el estado inicial del backend. Primero arranca el servidor, comprueba /health, ejecuta los tests y revisa que la base de datos está preparada.

A partir de ahí, cualquier cambio debería poder explicarse: qué endpoint afecta, qué regla de negocio modifica, qué datos toca y cómo se ha comprobado que sigue funcionando.
