06 · Implementación guiada: cómo codificar una funcionalidad completa

Este manual muestra cómo construir una parte del backend sin perderse entre archivos. La idea es que el alumnado vea el recorrido completo desde la entrada HTTP hasta la base de datos.

← Volver al índice

1. El error más común al empezar

Muchos alumnos abren el backend y quieren empezar directamente por el servicio o por Prisma, sin tener claro el recorrido completo. Eso suele acabar en código desordenado. Lo correcto es pensar la implementación como una cadena:

ruta → controlador → validador → servicio → repositorio → respuesta

Si entiendes ese flujo, cada nueva funcionalidad se vuelve mucho más manejable.

2. Ejemplo guiado: implementar GET /api/devices/:deviceId/schedule/today

Vamos a usar este endpoint como ejemplo porque combina varias capas, pero sigue siendo razonablemente comprensible.

Objetivo funcional: dado un dispositivo, devolver qué dosis tiene planificadas para hoy.

3. Paso 1: definir la ruta

// src/routes/deviceRoutes.ts
router.get('/:deviceId/schedule/today', getDeviceTodaySchedule)

Aquí no hay lógica todavía. Solo estamos diciendo que cuando llegue una petición GET a esa ruta, el controlador responsable será getDeviceTodaySchedule.

4. Paso 2: crear el controlador

// src/controllers/deviceController.ts
export async function getDeviceTodaySchedule(req, res, next) {
  try {
    const params = deviceIdParamSchema.parse(req.params)
    const schedule = await getTodayScheduleForDevice(params.deviceId)
    return res.status(200).json(schedule)
  } catch (error) {
    next(error)
  }
}

El controlador:

  • lee los parámetros de la URL;
  • los valida;
  • llama al servicio;
  • devuelve la respuesta;
  • si algo falla, delega el error al middleware global.

5. Paso 3: validar la entrada

// src/validators/deviceValidator.ts
export const deviceIdParamSchema = z.object({
  deviceId: z.string().cuid(),
})

Esto es muy útil porque detecta enseguida ids con formato incorrecto. El backend no debería llegar al repositorio con cualquier valor de deviceId.

6. Paso 4: escribir el servicio

// src/services/deviceService.ts
export async function getTodayScheduleForDevice(deviceId: string, now = new Date()) {
  const device = await findDeviceById(deviceId)
  if (!device) {
    throw new DeviceNotFoundError(deviceId)
  }

  const schedules = await findTodaySchedulesByDevice(deviceId, now)

  const doses = schedules.map((scheduledDose) => ({
    scheduledDoseId: scheduledDose.id,
    medicationName: scheduledDose.doseSchedule.medicationName,
    dosage: scheduledDose.doseSchedule.dosage,
    slotNumber: scheduledDose.doseSchedule.slotNumber,
    scheduledTime: scheduledDose.doseSchedule.scheduledTime.toISOString(),
    state: scheduledDose.state,
  }))

  return {
    deviceId: device.id,
    patientId: device.patientId ?? null,
    date: now.toISOString().slice(0, 10),
    doses,
  }
}

El servicio ya contiene decisiones reales: comprobar si el dispositivo existe, buscar sus dosis y dar forma a la respuesta final.

7. Paso 5: encapsular la consulta en el repositorio

// src/repositories/deviceRepository.ts
export async function findTodaySchedulesByDevice(deviceId: string, date: Date) {
  const startOfDay = new Date(Date.UTC(date.getUTCFullYear(), date.getUTCMonth(), date.getUTCDate(), 0, 0, 0, 0))
  const endOfDay = new Date(startOfDay)
  endOfDay.setUTCDate(startOfDay.getUTCDate() + 1)

  return prisma.scheduledDose.findMany({
    where: {
      deviceId,
      scheduledDate: {
        gte: startOfDay,
        lt: endOfDay,
      },
    },
    include: {
      doseSchedule: {
        include: {
          medicationPlan: true,
        },
      },
    },
  })
}

Aquí sí aparece la consulta concreta a base de datos. Gracias a separar esta parte, el servicio se mantiene más limpio.

8. Qué cambiaría en el ejemplo si implementaras POST /events

La lógica sería parecida, pero con un paso extra importante: validar el body según el tipo de evento.

const body = deviceEventBodySchema.parse(req.body)
const result = await handleDeviceEvent(params.deviceId, body)

Luego, en el servicio, habría que distinguir casos:

  • si el evento es device_online o heartbeat, normalmente se registra sin más;
  • si el evento es box_opened, hay que asociarlo a la dosis cuando proceda;
  • si el evento es dose_confirmed, hay que comprobar la dosis, el dispositivo y la ventana de tiempo.

9. Cómo pensar la lógica del evento dose_confirmed

La implementación no debería ser “si llega confirmación, marcar confirmed y ya está”. Debe recorrer varias comprobaciones:

1. buscar dispositivo
2. buscar dosis programada
3. comprobar que la dosis pertenece a ese dispositivo
4. comprobar que hay contexto suficiente para confirmarla
5. actualizar estado y confirmedAt
6. registrar evento

Este tipo de secuencia es una buena pista para extraer funciones pequeñas si el servicio empieza a crecer demasiado.

10. Patrón para implementar nuevas funcionalidades

1
Escribe primero qué debe hacer el endpoint.
No empieces por el código, empieza por la intención.
2
Decide inputs y outputs.
Params, body y respuesta.
3
Crea la ruta y el controlador.
Entrada HTTP clara.
4
Valida datos.
No dejes que la lógica reciba basura.
5
Implementa la lógica en el servicio.
Ahí se toman las decisiones.
6
Mueve consultas al repositorio.
Separa persistencia de negocio.
7
Prueba con Postman y con test.
No cierres una funcionalidad sin validarla.

11. Qué deberías evitar al codificar

  • Meter toda la lógica dentro del controlador
  • Hacer consultas Prisma directamente en cada ruta
  • Validar “a ojo” en lugar de usar el schema
  • Devolver respuestas inconsistentes entre endpoints parecidos
  • Añadir tipos de evento nuevos sin revisar el validador ni las pruebas.
Regla práctica: si una función mezcla lectura de params, validación, lógica, consulta a base de datos y composición de respuesta, seguramente deberías repartirla mejor.
