01 · Fundamentos: qué es un backend, qué es una API y qué es un endpoint

Este manual aclara la base conceptual del proyecto. Antes de hablar de archivos, rutas o tests, hay que entender qué papel tiene el backend dentro de VigiaSenior. Primero vamos a revisar los conceptos básicos Después, al final de la sección, tendrás un vídeo que explica la diferencia entre frontend y backend de forma visual, además de detallar el resto de conceptos. La idea es que puedas leer la explicación, ver el ejemplo y llegar al desarrollo de VigiaSenior con los conceptos bien entendidos.

1. Qué es un backend

Cuando una aplicación se divide en partes, solemos hablar de frontend y backend. El frontend es la parte visible con la que interactúa una persona usuaria. El backend es la parte que trabaja por detrás: recibe peticiones, procesa información, accede a la base de datos, aplica reglas y devuelve respuestas.

En VigiaSenior, el backend no es un adorno. Es el núcleo que interpreta lo que ocurre en el sistema. El pastillero o la simulación envían eventos; el backend decide si una toma está pendiente, abierta, confirmada o perdida; además, guarda histórico y genera alertas cuando corresponde.

2. Qué es una API

API significa Application Programming Interface. Dicho de forma sencilla, una API es una interfaz que permite que un sistema hable con otro. En lugar de botones o pantallas, utiliza peticiones y respuestas.

En este proyecto, la API permite que un dispositivo, una simulación o un panel consulten información y envíen eventos al servidor. Si no existiera esa API, el dispositivo no sabría dónde mandar la apertura de una cajita, ni el panel podría consultar alertas o el estado del paciente.

Sin APICon API
No hay contrato claro entre sistemas.Existe una forma acordada de pedir y devolver información.

3. Qué es un endpoint

Un endpoint es una ruta concreta de la API. Se identifica normalmente por una URL y por un método HTTP. Por ejemplo, GET /health o POST /api/devices/:deviceId/events.

Cada endpoint hace una tarea concreta. Si intentas meter demasiadas cosas en una sola ruta, el backend pierde claridad. Por eso conviene que cada endpoint responda a una pregunta concreta o realice una acción clara.

GET /health
→ sirve para comprobar que el servidor está levantado

GET /api/devices/:deviceId/schedule/today
→ devuelve la planificación del día para un dispositivo

POST /api/devices/:deviceId/events
→ recibe un evento generado por el dispositivo

El hardware no toma todas las decisiones. Puede detectar o simular una apertura, pero no decide por sí solo si la toma es válida. Esa decisión la toma el backend con ayuda de la base de datos y la lógica del proyecto.

5. La regla de negocio principal del proyecto

Todo el backend gira en torno a una regla central:

Una toma solo se considera correcta cuando existe apertura + confirmación dentro de una ventana de tiempo configurable.

Esta frase es más importante de lo que parece. Afecta a:

  • las entidades que debes modelar;
  • los eventos que debe aceptar la API;
  • los estados posibles de una toma;
  • las pruebas manuales y automáticas;
  • la información que después mostrará el dashboard.

6. Qué significa desarrollar el backend en este proyecto

Desarrollar el backend de VigiaSenior no es solo “hacer que responda Express”. Implica varias tareas distintas:

  • analizar el problema y entender el flujo del sistema;
  • diseñar un modelo de datos coherente;
  • definir una API clara;
  • escribir código organizado en capas;
  • validar la entrada que recibe el servidor;
  • persistir información en base de datos;
  • probar que la lógica hace lo que debe.

Cuando todo eso funciona de forma ordenada, puedes decir que tienes backend. Si solo tienes rutas que responden algo, todavía no.

8. Resumen de Conceptos

Antes de empezar con VigiaSenior, interesa tener clara una idea básica: una aplicación web suele dividirse en varias partes que trabajan juntas. El usuario no ve todo lo que ocurre por dentro; normalmente interactúa con una pantalla, pero detrás hay otros elementos que reciben información, la procesan y devuelven una respuesta.

En este proyecto nos vamos a centrar especialmente en el backend. Es decir, en la parte que trabaja por detrás: recibe peticiones, procesa datos, consulta la base de datos, aplica reglas de negocio y responde al frontend, al dispositivo o a la simulación.
