05 · Diseño de la API y endpoints reales del proyecto

Este manual baja a lo concreto: qué rutas tiene el backend, qué devuelve cada una y cómo interpretar los cuerpos JSON del proyecto.

← Volver al índice

1. La API no se diseña por ocurrencias

Una API buena no nace de poner rutas al azar, sino de responder preguntas reales del sistema. En VigiaSenior, las preguntas son:

  • ¿está vivo el backend?
  • ¿qué plan del día tiene un dispositivo?
  • ¿qué evento ha enviado el dispositivo?
  • ¿qué estado global tiene un paciente?
  • ¿qué alertas siguen abiertas?
  • ¿cómo se resuelve una alerta?

2. Endpoints mínimos actuales

GET    /health
GET    /api/devices/:deviceId/schedule/today
POST   /api/devices/:deviceId/events
GET    /api/patients/:patientId/dashboard
GET    /api/patients/:patientId/alerts
PATCH  /api/alerts/:alertId/resolve

3. GET /health

Es el endpoint más simple, pero muy útil para comprobar que el servidor está levantado y responde.

GET /health

Respuesta esperada:

{
  "status": "ok",
  "uptime": 123.45,
  "timestamp": "2026-05-25T21:00:00.000Z"
}

Si este endpoint falla, no tiene sentido probar el resto todavía.

4. GET /api/devices/:deviceId/schedule/today

Esta ruta devuelve la planificación del día para un dispositivo concreto. El parámetro deviceId viaja por la URL y se valida antes de usarlo.

GET /api/devices/cm1234567890abcde1234567/schedule/today

Respuesta típica:

{
  "deviceId": "cm1234567890abcde1234567",
  "patientId": "cm7654321...",
  "date": "2026-05-25",
  "confirmationTimeoutSeconds": 60,
  "doses": [
    {
      "scheduledDoseId": "cmDose01",
      "doseScheduleId": "cmSchedule01",
      "medicationName": "Aspirina",
      "dosage": "1 comprimido",
      "slotNumber": 1,
      "scheduledTime": "2026-05-25T08:00:00.000Z",
      "windowMinutesBefore": 10,
      "windowMinutesAfter": 15,
      "requiresConfirmation": true,
      "state": "scheduled"
    }
  ]
}

Esta ruta es importante porque conecta el plan abstracto con lo que debe hacer el dispositivo en el día actual.

5. POST /api/devices/:deviceId/events

Esta es una de las rutas más importantes del proyecto. Recibe eventos enviados por el dispositivo o por la simulación.

El cuerpo se valida con Zod usando una unión discriminada por eventType. Eso significa que el formato del payload cambia según el tipo de evento.

{
  "eventType": "box_opened",
  "timestamp": "2026-05-25T08:01:00.000Z",
  "payload": {
    "slotNumber": 1,
    "doseId": "cmDose01"
  }
}

Otro ejemplo:

{
  "eventType": "dose_confirmed",
  "timestamp": "2026-05-25T08:01:20.000Z",
  "payload": {
    "doseId": "cmDose01",
    "method": "button"
  }
}

Respuesta esperada:

{
  "eventId": "cmEvent01",
  "status": "accepted",
  "receivedAt": "2026-05-25T08:01:20.500Z"
}

6. GET /api/patients/:patientId/dashboard

Esta ruta construye una vista resumida del estado de un paciente. Su respuesta es más compleja porque no devuelve un solo dato, sino una composición de varias consultas y transformaciones.

En líneas generales incluye:

  • datos básicos del paciente;
  • estado del dispositivo;
  • próximas tomas;
  • tomas de hoy;
  • alertas activas;
  • resumen de cumplimiento.

El alumnado no tiene que memorizar todo el JSON, pero sí entender que esta ruta requiere composición de datos y no una simple consulta plana.

7. GET /api/patients/:patientId/alerts

Devuelve las alertas de un paciente junto con contadores de abiertas y resueltas. Es útil para enseñar que una API también puede devolver información resumida y no solo listas crudas.

{
  "patientId": "cmPatient01",
  "alerts": [ ... ],
  "total": 3,
  "openCount": 2,
  "resolvedCount": 1
}

8. PATCH /api/alerts/:alertId/resolve

Esta ruta modifica el estado de una alerta. No crea un recurso nuevo ni consulta una lista: cambia una parte del recurso existente. Por eso PATCH encaja bien aquí.

La lógica del servicio comprueba primero si la alerta existe y después si realmente sigue abierta. Si no está abierta, devuelve conflicto.

9. Validación y errores

No todas las peticiones son válidas. Por ejemplo:

  • si el deviceId no tiene formato CUID, la validación falla antes de entrar en la lógica;
  • si el evento dose_confirmed no incluye doseId, el body es inválido;
  • si la dosis no pertenece al dispositivo actual, el servicio rechaza la operación;
  • si el recurso no existe, se devuelve 404.

Esto enseña al alumnado que un backend serio no acepta cualquier cosa sin comprobarla.

10. Cómo debería documentarse la API del proyecto

Al menos, cada equipo debería dejar por escrito:

  • la lista de endpoints;
  • el método HTTP de cada uno;
  • qué params recibe;
  • qué body espera, si aplica;
  • qué estructura devuelve;
  • qué errores principales contempla.

Con eso, otra persona puede probar la API sin tener que abrir todos los archivos del backend.

Estos apuntes están pensados como soporte real de trabajo. La idea es que el alumnado pueda usarlos mientras diseña, implementa, prueba y documenta el backend.
