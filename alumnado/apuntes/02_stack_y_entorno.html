02 · Stack real del proyecto y preparación del entorno

Este manual explica con qué tecnologías se construye el backend actual y qué necesita el alumnado para poder ejecutarlo y tocarlo sin romperlo todo.

← Volver al índice

1. Qué stack usa el backend actual

El backend de VigiaSenior está organizado con un stack típico de servidor en JavaScript/TypeScript:

  • Node.js como entorno de ejecución;
  • npm para gestionar dependencias y scripts;
  • TypeScript para tipar el código;
  • Express para definir el servidor HTTP y las rutas;
  • Prisma como ORM y cliente de acceso a base de datos;
  • Zod para validar parámetros y cuerpos de petición;
  • Jest y Supertest para pruebas.

Esto significa que aquí no se trabaja con Django como framework principal. La lógica general del proyecto sí sigue siendo la misma, pero la implementación está adaptada al stack real del repositorio.

3. Scripts del proyecto: por qué son importantes

En la mayoría de repos modernos no se ejecutan los comandos a mano uno por uno. Se agrupan en scripts dentro de package.json. Esto hace que todo el equipo use el mismo flujo.

{
  "scripts": {
    "dev": "ts-node-dev --respawn --transpile-only src/server.ts",
    "build": "tsc",
    "test": "jest --runInBand",
    "prisma:generate": "npx prisma generate",
    "prisma:migrate": "npx prisma migrate dev --name init",
    "prisma:seed": "npx prisma db seed"
  }
}

Si el alumnado aprende a usar estos scripts, no necesita memorizar comandos largos en cada sesión.

4. Qué significa cada script

  • npm run dev → arranca el servidor en modo desarrollo y reinicia al detectar cambios.
  • npm run build → compila el proyecto TypeScript.
  • npm test → ejecuta las pruebas.
  • npm run prisma:generate → genera el cliente de Prisma a partir del schema.
  • npm run prisma:migrate → aplica migraciones de base de datos.
  • npm run prisma:seed → carga datos iniciales si existe script de seed.

5. Preparación del entorno local

El orden recomendado es este:

git clone <url-del-repo>
cd implementacion/backend
npm install
cp .env.example .env
npm run prisma:generate
npm run prisma:migrate
npm run prisma:seed
npm run dev

Puede haber pequeñas variaciones según el sistema operativo o el estado de la base de datos, pero esta secuencia es una base razonable para empezar.

6. Qué papel tiene el archivo .env

El archivo .env guarda variables de entorno. En proyectos de backend se usa para separar configuración sensible del código fuente. Un ejemplo típico sería la ruta de la base de datos o el puerto del servidor.

PORT=3000
DATABASE_URL="file:./dev.db"

La idea no es esconder magia, sino evitar que ciertos valores queden dispersos por el código o comprometidos en el repositorio.

7. TypeScript: por qué no trabajar directamente en JavaScript

TypeScript añade tipado y comprobaciones que ayudan bastante en backend. No evita todos los errores, pero sí varios muy comunes:

  • pasar un tipo de dato incorrecto a una función;
  • acceder a una propiedad que no existe;
  • olvidar la forma que debería tener un objeto de respuesta.
interface DeviceScheduleTodayResponse {
  deviceId: string;
  patientId: string | null;
  date: string;
  confirmationTimeoutSeconds: number;
  doses: DeviceDoseScheduleItem[];
}

Un alumno no necesita dominar todo el sistema de tipos para empezar, pero sí entender que esas definiciones ayudan a hacer el código más claro y menos frágil.

8. Git y organización mínima del trabajo

Antes de tocar el servidor conviene tener el repositorio en orden. El flujo básico sigue siendo:

git status
git add .
git commit -m "feat: añade endpoint de health"
git push

La trazabilidad importa también en un proyecto académico. Si el alumnado hace cambios ordenados y con mensajes razonables, luego puede explicar mejor el proceso seguido.

9. Checklist de entorno listo

  • Node y npm instalados;
  • dependencias instaladas con npm install;
  • archivo .env creado a partir del ejemplo;
  • cliente Prisma generado;
  • migraciones aplicadas;
  • datos de seed cargados, si procede;
  • servidor arrancando con npm run dev;
  • endpoint /health accesible.
Consejo práctico: no empieces a programar una nueva ruta si todavía no has comprobado que el proyecto levanta correctamente.

Estos apuntes están pensados como soporte real de trabajo. La idea es que el alumnado pueda usarlos mientras diseña, implementa, prueba y documenta el backend.
