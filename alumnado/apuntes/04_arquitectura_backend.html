04 · Arquitectura del backend: rutas, controladores, servicios, repositorios y validadores

Este manual explica cómo está organizada la implementación y qué responsabilidad tiene cada capa. Comprender esta arquitectura evita mezclar todo en un solo archivo.

← Volver al índice

1. Por qué separamos el código en capas

En proyectos pequeños puede parecer más rápido ponerlo todo dentro de una misma función. El problema es que eso tiene poca escalabilidad si el proyecto crece: cuesta leerlo, cuesta probarlo y cuesta cambiarlo. Por eso, el backend de VigiaSenior se organiza por capas.

La idea es sencilla: cada capa debería tener una responsabilidad principal. Así se entiende mejor el código y se mantiene mejor.

Antes de entrar en el detalle de rutas, controladores, servicios, repositorios y validadores, merece la pena ver este vídeo sobre arquitectura por capas. Lo ponemos al principio porque esta idea va a marcar cómo se entiende el resto de la sección: si cada capa tiene clara su responsabilidad, el backend será mucho más fácil de leer, probar y modificar.

2. Vista global de la estructura

src/
├── app.ts
├── server.ts
├── routes/
├── controllers/
├── services/
├── repositories/
├── validators/
├── prisma/
└── types/

A esta estructura se suman las carpetas de tests/ para validar comportamiento del backend.

3. app.ts y server.ts: no son lo mismo

Una separación muy útil es distinguir entre la aplicación Express y el arranque del servidor.

  • app.ts configura middlewares, rutas y manejo global de errores.
  • server.ts se encarga de escuchar en un puerto concreto.
// app.ts
app.use(express.json())
app.use('/api/devices', deviceRoutes)
app.use('/api/patients', patientRoutes)
app.use('/api', alertRoutes)

Gracias a esto, en pruebas se puede importar la app sin necesidad de levantar un servidor real escuchando un puerto.

4. Rutas: qué deben hacer y qué no

Las rutas solo deberían declarar el camino de entrada y salida hacia el controlador. No deberían contener lógica pesada.

router.get('/:deviceId/schedule/today', getDeviceTodaySchedule)
router.post('/:deviceId/events', postDeviceEvent)

Una buena ruta se entiende de un vistazo. El lector sabe qué método HTTP usa, qué recurso toca y qué controlador se ejecutará.

5. Controladores: traducen request y response

El controlador recibe la petición, extrae parámetros, valida entradas y delega en la capa de servicio. Después construye la respuesta HTTP.

export async function postDeviceEvent(req, res, next) {
  try {
    const params = deviceIdParamSchema.parse(req.params)
    const body = deviceEventBodySchema.parse(req.body)

    const result = await handleDeviceEvent(params.deviceId, body)
    return res.status(201).json(result)
  } catch (error) {
    next(error)
  }
}

El controlador no debería decidir la regla de negocio completa. Su papel es orquestar la entrada y la salida.

6. Servicios: aquí vive la lógica de negocio

La capa de servicio es probablemente la más importante a nivel funcional. Aquí se decide qué hacer realmente con la información recibida.

Por ejemplo, cuando llega un dose_confirmed, el servicio debe:

  • comprobar si el dispositivo existe;
  • buscar la dosis programada;
  • verificar que esa dosis pertenece al dispositivo actual;
  • marcar la toma como confirmada si procede;
  • crear el evento en la base de datos;
  • devolver una respuesta clara.
const saved = await createDeviceEvent(deviceId, event, patientId)

return {
  eventId: saved.id,
  status: 'accepted',
  receivedAt: saved.createdAt.toISOString(),
}

7. Repositorios: hablar con la base de datos sin ensuciar la lógica

Los repositorios encapsulan las consultas a la base de datos. Así el servicio no se llena de llamadas Prisma mezcladas con decisiones de negocio.

export async function findDeviceById(deviceId: string) {
  return prisma.device.findUnique({
    where: { id: deviceId },
    select: {
      id: true,
      patientId: true,
    },
  })
}

Esto hace que el servicio pueda leerse como lógica y no como una secuencia interminable de consultas.

8. Validadores: proteger la API antes de tocar la lógica

La API recibe datos externos. Por eso conviene validar cuanto antes si los parámetros y cuerpos tienen la forma correcta. Aquí se usa Zod.

export const deviceIdParamSchema = z.object({
  deviceId: z.string().cuid(),
})
export const deviceEventBodySchema = z.discriminatedUnion('eventType', [
  z.object({
    eventType: z.literal('device_online'),
    timestamp: z.string().datetime(),
    payload: z.object({ batteryPercent: z.number().min(0).max(100).optional() }),
  }),
  ...
])

Esto evita que la lógica trabaje con cuerpos mal formados, ids con formato incorrecto o timestamps inválidos.

9. types/: por qué no es una carpeta decorativa

Los tipos ayudan a que el proyecto sea más legible. No solo sirven para que compile: también documentan el contrato entre capas.

export interface DeviceEventResponse {
  eventId: string
  status: 'accepted'
  receivedAt: string
}

Cuando un alumno ve ese tipo, entiende mucho mejor qué debe devolver el servicio o el controlador sin tener que adivinarlo.

Estos apuntes están pensados como soporte real de trabajo. La idea es que el alumnado pueda usarlos mientras diseña, implementa, prueba y documenta el backend.
