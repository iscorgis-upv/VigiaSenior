08 · Pruebas automáticas con Jest y Supertest

Este manual explica cómo se prueban la lógica y los endpoints de forma automática. No se trata de testear por moda, sino de tener evidencias de que el backend se comporta como debería.

← Volver al índice

1. Qué diferencia hay entre prueba manual y automática

Tipo de pruebaVentajaLimitación
Manual con Postmanrápida y visualdepende de que alguien la ejecute
Automática con Jestrepetible y verificablerequiere escribir código de test

En un proyecto serio, ambas se complementan. Postman ayuda a explorar; Jest ayuda a asegurar.

2. Qué es Jest

Jest es un runner de pruebas para JavaScript/TypeScript. Permite definir casos de prueba, agruparlos y ejecutarlos de forma repetible.

describe('GET /health', () => {
  it('returns 200 OK', async () => {
    await request(app).get('/health').expect(200)
  })
})

La estructura básica es muy parecida a lenguaje natural:

  • describe agrupa una funcionalidad;
  • it o test define un caso concreto;
  • expect expresa lo que se espera.

3. Qué aporta Supertest

Supertest permite lanzar peticiones HTTP contra la aplicación Express dentro de una prueba. Es decir, simula el comportamiento de un cliente sin necesidad de abrir Postman.

const response = await request(app)
  .get('/health')
  .expect(200)

Esto es especialmente útil para pruebas de integración de endpoints.

4. Tipos de prueba presentes en el proyecto

  • Integration tests: prueban endpoints como /health, /schedule/today o /dashboard.
  • Unit tests: prueban reglas de lógica, por ejemplo la confirmación de dosis.

El alumnado debería distinguir ambos niveles. Una prueba de integración comprueba varias capas a la vez; una unitaria aísla una parte más concreta.

5. Ejemplo sencillo de integración: health

describe('GET /health', () => {
  it('returns 200 OK', async () => {
    await request(app).get('/health').expect(200)
  })

  it('returns a basic health response structure', async () => {
    const response = await request(app).get('/health').expect(200)

    expect(response.body).toEqual(
      expect.objectContaining({
        status: expect.any(String),
      }),
    )
    expect(response.body.status).toBe('ok')
  })
})

Este tipo de test es muy didáctico porque enseña a comprobar tanto el código HTTP como la forma de la respuesta.

6. Ejemplo de prueba unitaria más cercana al dominio

En el proyecto aparecen pruebas centradas en la regla de cumplimiento de la dosis. La idea es comprobar casos como estos:

  • si solo hay apertura sin confirmación, la dosis no debe quedar confirmada;
  • si llega una confirmación sin apertura previa, debe rechazarse;
  • si la confirmación llega fuera de la ventana, debe rechazarse;
  • si apertura y confirmación ocurren dentro de la ventana, la dosis debe pasar a confirmada.

Ese tipo de pruebas son muy valiosas porque están alineadas con la regla principal del proyecto y no con un detalle secundario.

7. beforeAll, afterAll y limpieza de datos

Muchos tests crean pacientes, dispositivos, planes o dosis de prueba. Para que el entorno no se ensucie, conviene preparar los datos al principio y eliminarlos al final.

beforeAll(async () => {
  // crear caregiver, patient, device...
})

afterAll(async () => {
  // borrar datos de prueba y desconectar prisma
})

Esta estructura ayuda a que las pruebas sean repetibles y no fallen por residuos de ejecuciones anteriores.

8. Qué debería comprobar el alumnado en cada test

  • el código de estado HTTP esperado;
  • que la respuesta sea JSON cuando corresponda;
  • que aparezcan las propiedades mínimas del contrato;
  • que la base de datos refleje el cambio esperado;
  • que los casos erróneos se rechacen con sentido.
Idea importante: un test útil no solo comprueba que “hay respuesta”; comprueba que esa respuesta tiene el significado esperado dentro del negocio.

9. Cómo ejecutar y leer los resultados

npm test

Cuando una prueba falla, no conviene mirar solo la línea roja. Hay que leer:

  • qué archivo de test falló;
  • qué caso concreto falló;
  • qué esperaba y qué recibió;
  • si el problema viene del endpoint, del servicio o de los datos creados.

10. Qué debería quedar como base mínima de validación

  • tests de salud del servidor;
  • tests de los endpoints principales;
  • al menos una batería clara sobre la regla apertura + confirmación;
  • datos de prueba coherentes y aislados;
  • capacidad de ejecutar la suite sin intervención manual extraña.

Si el alumnado llega a ese punto, ya dispone de una base de calidad bastante sólida para un proyecto de este tipo.
