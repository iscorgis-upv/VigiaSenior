03 · Modelado del dominio, base de datos y lectura del schema de Prisma

En este manual se explica qué datos necesita el sistema, cómo se relacionan y cómo se representan en el schema actual del proyecto.

← Volver al índice

1. Por qué el modelo de datos importa tanto

Un backend puede tener rutas y tests, pero si el modelo de datos está mal planteado, el sistema acaba volviéndose incoherente. En VigiaSenior, la base de datos es lo que permite reconstruir el estado del dispositivo, del paciente, de las tomas y de las alertas.

Dicho de otro modo: la lógica de negocio necesita memoria. Esa memoria es la base de datos.

Aunque la finalidad principal del proyecto no es diseñar una base de datos desde cero, se proporcionará una estructura inicial para poder centrarnos en las operaciones más importantes desde el backend: conexión, consulta, creación, actualización y borrado de datos.

2. Entidades principales del proyecto

El dominio del proyecto gira alrededor de estas entidades:

  • Caregiver: la persona cuidadora o responsable.
  • Patient: la persona paciente a la que se asocia la medicación.
  • Device: el dispositivo físico o lógico del pastillero.
  • MedicationPlan: el plan de medicación general.
  • DoseSchedule: una pauta concreta, con medicamento, dosis, slot y hora.
  • ScheduledDose: la instancia diaria que se va a ejecutar o controlar.
  • DeviceEvent: los eventos enviados por el dispositivo.
  • Alert: las incidencias o avisos que el sistema registra.

3. Cómo pensar estas relaciones en lenguaje normal

RelaciónCómo se entiende
Caregiver → PatientUna persona cuidadora puede supervisar a varios pacientes.
Patient → DeviceUn paciente puede tener uno o más dispositivos asociados, según diseño.
Patient → MedicationPlanUn paciente puede tener distintos planes de medicación.
MedicationPlan → DoseScheduleUn plan contiene varias pautas concretas.
DoseSchedule → ScheduledDoseCada pauta se materializa en tomas programadas reales.
Device → DeviceEventEl dispositivo genera eventos a lo largo del tiempo.
ScheduledDose → AlertUna toma concreta puede provocar alertas.

4. Qué hace Prisma en este proyecto

Prisma es un ORM. Eso significa que ayuda a trabajar con la base de datos desde código, sin escribir siempre SQL manual. En lugar de definir tablas a mano en un primer momento, aquí se trabaja con un archivo schema.prisma donde se describen modelos, campos y relaciones.

generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "sqlite"
  url      = env("DATABASE_URL")
}

Eso indica que el proveedor actual es SQLite y que Prisma generará un cliente de acceso para usarlo desde TypeScript.

5. Lectura guiada de algunos modelos reales

model Device {
  id        String   @id @default(cuid())
  serial    String   @unique
  name      String
  boxCount  Int
  active    Boolean
  patientId String
  patient   Patient  @relation(fields: [patientId], references: [id])
}

Este modelo nos dice varias cosas importantes:

  • el identificador principal es id y se genera automáticamente con cuid();
  • el número de serie debe ser único;
  • cada dispositivo está asociado a un paciente;
  • la relación se materializa con la clave foránea patientId.

6. Ejemplo clave: ScheduledDose

model ScheduledDose {
  id                   String   @id @default(cuid())
  doseScheduleId       String
  deviceId             String
  patientId            String
  scheduledDate        DateTime
  state                String
  openedAt             DateTime?
  confirmedAt          DateTime?
  confirmationDeadline DateTime
}

Este es uno de los modelos más importantes del proyecto porque captura el estado real de la toma. No guarda solo la pauta abstracta, sino la ejecución que hay que vigilar en una fecha concreta.

Aquí aparecen varias pistas de lógica:

  • state representa el estado actual de la toma;
  • openedAt guarda cuándo se abrió la cajita, si ocurrió;
  • confirmedAt guarda cuándo se confirmó la dosis, si ocurrió;
  • confirmationDeadline marca el límite para considerar válida la confirmación.

7. DeviceEvent: el histórico de lo que llega al backend

model DeviceEvent {
  id        String   @id @default(cuid())
  deviceId  String
  patientId String
  type      String
  timestamp DateTime
  payload   String
}

Este modelo es importante porque conserva el registro bruto de eventos. A partir de ahí el sistema puede reconstruir o justificar decisiones posteriores.

El campo payload se guarda como texto serializado. Esto permite conservar el contenido del evento, aunque luego se interprete desde código.

8. Alert: cómo se representa una incidencia

model Alert {
  id              String    @id @default(cuid())
  patientId       String
  deviceId        String
  scheduledDoseId String?
  type            String
  severity        String
  status          String
  message         String
}

Una alerta no es solo un texto. Tiene tipo, severidad y estado. Eso permite consultar qué sigue abierto, qué ya se resolvió y qué prioridad tiene cada caso.

9. Qué debería comprender el alumnado del schema

  • qué entidades son centrales y cuáles son auxiliares;
  • qué relaciones unen a unas con otras;
  • qué campos son obligatorios y cuáles opcionales;
  • qué datos permiten aplicar la regla de negocio;
  • por qué el backend necesita tanto el modelo abstracto como el histórico de eventos.

10. Actividad de cierre recomendada

Antes de seguir con la API, conviene que cada equipo haga dos cosas:

  • dibujar su propio diagrama simplificado del dominio en papel o herramienta visual;
  • explicar con una frase para qué sirve cada modelo principal del schema.

Si el alumnado no puede explicar el modelo con palabras normales, todavía no lo domina lo suficiente para implementar con seguridad.

Estos apuntes están pensados como soporte real de trabajo. La idea es que el alumnado pueda usarlos mientras diseña, implementa, prueba y documenta el backend.
