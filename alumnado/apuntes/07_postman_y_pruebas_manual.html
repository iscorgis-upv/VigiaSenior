07 · Cómo probar el backend con Postman paso a paso

Este manual se centra en las pruebas manuales. La idea es que el alumnado pueda comprobar el backend creando las peticiones manualmente desde Postman. Como en apartados anteriores, hemos incorporado un vídeo de apoyo sobre el uso básico de Postman. La herramienta ofrece muchas opciones y al principio es fácil perderse entre ellas, así que el objetivo es centrarse en lo esencial: crear peticiones, probar operaciones CRUD, revisar códigos de estado y entender qué está respondiendo el backend.

← Volver al índice

1. Por qué Postman es útil aquí

Postman permite enviar peticiones HTTP al backend y ver la respuesta de forma clara. Para alumnado, esto tiene una ventaja enorme: puedes validar una ruta sin depender de una interfaz gráfica o del dispositivo físico.

Si el equipo entiende cómo probar con Postman, puede cerrar más rápidamente problemas de rutas, cuerpos JSON, errores 400/404 o respuestas mal construidas.

2. Configuración mínima recomendada

Lo primero es crear un entorno con una variable base. Así no hace falta escribir la URL completa en cada petición.

Entorno: VigiaSenior local
baseUrl = http://127.0.0.1:3000

Después se crea una colección llamada, por ejemplo, VigiaSenior Backend.

3. Primera petición: health

GET {{baseUrl}}/health

Esta debería ser la primera prueba siempre. Si no responde 200, el problema no está en un controlador concreto: seguramente el servidor ni siquiera está bien levantado.

Qué comprobar:

  • código de estado 200;
  • cabecera JSON;
  • campo status con valor ok.

4. Probar la planificación del dispositivo

GET {{baseUrl}}/api/devices/<deviceId>/schedule/today

Para esta prueba necesitas un deviceId válido existente en la base de datos. Si no lo tienes, puedes extraerlo del seed, de una consulta previa o del panel de administración que estéis usando.

Qué deberías revisar:

  • si la ruta responde 200;
  • si devuelve un deviceId coherente;
  • si aparece un array doses;
  • si cada dosis tiene los campos que espera el contrato.

5. Probar el registro de eventos

Esta prueba es central porque toca validación, persistencia y, en algunos casos, lógica.

Ejemplo de box_opened:

POST {{baseUrl}}/api/devices/<deviceId>/events
Content-Type: application/json

{
  "eventType": "box_opened",
  "timestamp": "2026-05-25T08:01:00.000Z",
  "payload": {
    "slotNumber": 1,
    "doseId": "cmDose01"
  }
}

Ejemplo de dose_confirmed:

{
  "eventType": "dose_confirmed",
  "timestamp": "2026-05-25T08:01:20.000Z",
  "payload": {
    "doseId": "cmDose01",
    "method": "button"
  }
}

6. Qué errores manuales conviene provocar a propósito

No todo consiste en probar el caso feliz. También conviene forzar algunos errores para comprobar que el backend reacciona bien:

  • mandar un deviceId con formato incorrecto;
  • omitir doseId en un dose_confirmed;
  • enviar un método no permitido en method;
  • usar un doseId inexistente;
  • intentar confirmar una dosis fuera de ventana.

Estas pruebas enseñan al alumnado que la calidad de una API no se mide solo por responder cuando todo va bien.

7. Probar dashboard y alertas

GET {{baseUrl}}/api/patients/<patientId>/dashboard
GET {{baseUrl}}/api/patients/<patientId>/alerts

Aquí conviene observar si la respuesta está realmente compuesta, no solo si llega algo. Por ejemplo:

  • si el dashboard incluye paciente, dispositivo, próximas tomas y resumen;
  • si las alertas llevan contadores y estado;
  • si los ids de paciente y dispositivo son coherentes con los datos sembrados.

8. Probar resolución de alertas

PATCH {{baseUrl}}/api/alerts/<alertId>/resolve

Después de resolver una alerta, puedes volver a pedir el listado del paciente y comprobar si el contador de abiertas disminuye y el estado ha cambiado.

Esto es útil para enseñar que una prueba no siempre termina en una sola petición; a veces hay que encadenar varias para comprobar el efecto real.

9. Tests dentro de Postman

Postman también permite añadir pequeños scripts de test. No sustituyen a Jest, pero ayudan a validar rápidamente respuestas repetitivas.

pm.test("Status code is 200", function () {
  pm.response.to.have.status(200);
});

pm.test("Response is JSON", function () {
  pm.response.to.be.json;
});

También se pueden guardar variables de respuesta para reutilizarlas en peticiones posteriores.

Health.

Consultar si hay incidencias.

Resolve alert.
Comprobar modificación de estado.

Estos apuntes están pensados como soporte real de trabajo. La idea es que el alumnado pueda usarlos mientras diseña, implementa, prueba y documenta el backend.
